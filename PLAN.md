# План работы — PandoraClinica

Рабочий план команды. Владельцы: **Б** — бэкендщик, **Ф** — фронтендщик, **Я** — фуллстак
(интеграция, девопс, основа фронта). Порядок внутри разделов = приоритет. Зависимости
отмечены отдельно. Сроки не привязаны: задача считается следующей, когда закрыта
предыдущая из её зависимостей.

---

## 0. Принятые решения

- **Стек фронта:** Vite + React + TypeScript, компонентная библиотека — Ant Design
  (таблицы/формы/дейтпикеры — основа интерфейсов регистратуры и админа).
  Если фронтендщик уже спроектировал макеты под другую библиотеку — пересогласовать.
- **Контракт фронт↔бэк:** типизированный API-клиент, автогенерируемый из OpenAPI
  (`openapi-typescript` + `openapi-fetch`). Бэк меняет API → фронт перегенерирует
  типы → TypeScript подсвечивает сломанные места.
- **Структура фронта:** `frontend/` — монорепо из трёх пакетов:
  `staff` (внутреннее приложение), `public` (внешний сайт), `shared` (API-клиент,
  auth, общие типы и утилиты).
- **Роли:** admin / registrar / doctor (+ табло без авторизации, доступ из локальной сети).

## 1. Бэкенд — задачи

### B1. Тесты в CI — владелец: Б (или Я) — ✅ готово
**Что:** второй job в `.github/workflows/ci.yml` помимо линтинга.
**Состав:**
- service-контейнер PostgreSQL 17 (образ `postgres:17`, health-check `pg_isready`,
  порты 5432, учётка/база из переменных окружения);
- установка зависимостей из `backend/requirements.txt`;
- прогон `pytest` (conftest сам пересоздаёт тестовую базу `pandora_clinic_test`
  и накатывает схему через `Base.metadata.create_all` — миграции в тестах не нужны).
**Критерий готовности:** оба job зелёные на main; упавший тест роняет CI.
**Зависимости:** нет. Блокирует: дисциплину PR (см. B8).

### B2. Демо-сид — владелец: Б — **блокер для всех экранов фронта** — ✅ готово
**Что:** расширить `app/seed.py` режимом демо-данных.
**Состав:**
- специальности (Терапия, УЗИ, Кардиология…);
- 3–4 врача с учётками (роль doctor, известные пароли для демо);
- кабинеты: 2 обычных + 1 УЗИ (проверить типизацию кабинетов);
- недельные шаблоны графиков для каждого врача;
- генерация слотов на 14 дней вперёд (готовым эндпоинтом генерации);
- 2–3 пациента (гражданин РФ с СНИЛС, иностранец со страховкой);
- запуск: `python -m app.seed --demo` (без флага — только первый админ, как сейчас).
**Критерий готовности:** после `--demo` на пустой базе фронт показывает утренний
экран с врачами, слоты на запись, табло с очередью.

### B3. Сужение CORS — владелец: Б
**Что:** убрать `allow_origins=["*"]` из `main.py`.
**Состав:** переменная окружения `CORS_ORIGINS` (список через запятую), дефолт для
разработки — порты локальных фронтов (5173, 5174).
**Критерий готовности:** запросы с локальных фронтов проходят, с постороннего
origin — блокируются.
**Зависимости:** появление каркаса фронта (F1) — чтобы знать адреса.

### B4. Расторжение договора — владелец: Б
**Что:** эндпоинт завершения договора (статусы в схеме есть, ручки нет).
**Состав:**
- `POST /api/admin/doctors/{doctor_id}/contract/terminate`;
- валидации: договор существует и в статусе active;
- решение по будущим слотам расторгнутого врача (по бизнес-правилу: блокировать,
  существующие записи — отменять или доигрывать; согласовать с командой);
- тест на полный путь: найм → расторжение → слоты заблокированы.
**Критерий готовности:** контракт lifecycle полный (draft → active → terminated/expired).

### B5. Вечерняя автоотправка выгрузки — владелец: Б
**Что:** автоматическая выгрузка приёмов за день в «облако» (имитация).
**Состав:**
- планировщик (APScheduler) — ежедневно в 19:00 (до сервисного окна 20:00);
- выгрузка тем же кодом, что ручной эндпоинт, раздельно РФ / не-РФ;
- приёмник-имитация: локальный каталог (например `./exports/`) или
  S3-совместимое хранилище, настраивается переменной окружения;
- ретраи при неудаче + журнал отправок;
- ручной эндпоинт остаётся для админ-интерфейса.
**Критерий готовности:** в каталоге-имитации сами появляются два файла за прошедший
день; при недоступности — повтор с записью в журнал.

### B6. Прод-гигиена — владелец: Б + Я
**Состав:**
- `SECRET_KEY` только из окружения (без dev-дефолта в проде — предупреждение при
  старте, если не задан);
- учётка первого админа: генерировать пароль или принудительная смена при первом
  входе (сейчас `admin/admin`);
- `.env.example` со всеми переменными и комментариями.
**Критерий готовности:** чек-лист безопасности пройден перед показом заказчику.

### B7. Профиль врача (детальный) — владелец: Б — **решение команды: включить или выбросить**
В AGENTS помечен как отложенный. Если включаем: расширенные поля профиля + эндпоинт
чтения. Если нет — зафиксировать в AGENTS как вне скоупа, чтобы не висело.

### B8. Процесс в AGENTS.md — владелец: Я
**Состав:**
- раздел «Ветки и ревью»: фича-ветки → PR → зелёный CI → ревью → main;
  branch protection на main (запрет прямых push);
- раздел «Развёртывание и эксплуатация»: docker-compose, окно обновлений 20:00–6:00,
  бэкапы (см. D3), секреты, процедура деплоя;
- обновить README под новую модель (одна ветка main удалена ветка feature/backend).
**Критерий готовности:** новый участник поднимает окружение по README за 15 минут.

## 2. Фронтенд — основа (каркас) — владелец: Я

Граница: каркас и инфраструктура, **не** готовые экраны. Экраны делает Ф.

### F1. Монорепо `frontend/` — ✅ готово (npm workspaces)
- `staff` и `public` — Vite + React + TS, общий `tsconfig.base.json`;
- `shared` — пакет с API-клиентом, типами, auth-обвязкой (импорт из обоих приложений);
- dev-порты: staff 5173, public 5174, прокси `/api` на `localhost:8000`;
- команды: `npm run dev` (оба), `npm run build`, `npm run lint`.

### F2. Типизированный API-клиент — ✅ готово (схема закоммичена)
- `openapi-typescript` генерирует типы из `http://localhost:8000/openapi.json`;
- `openapi-fetch` — типизированные вызовы без ручных обёрток;
- скрипт `npm run gen:api`; сгенерированные типы коммитятся (чтобы CI фронта
  не зависел от запущенного бэка).
- хелперы: единая обработка 401 (разлогин) и ошибок валидации (422) с русскими
  сообщениями.

### F3. Auth-обвязка — ✅ готово
- страница логина (на Ant Design Form);
- auth-context: токен в localStorage, запрос `/api/auth/login`, выход по 401;
- guards: `RequireRole`-обёртка маршрутов, редирект на логин;
- после входа — редирект на домашнюю страницу по роли (регистратор → утро,
  врач → мой день, админ → персонал).

### F4. Каркас интерфейса — ✅ готово (табло — маршрут /board в public)
- Ant Design Layout: сайдбар с меню **по роли**, хедер с именем пользователя и выходом;
- страницы-заглушки под все экраны из раздела 3 с реальными роутами и названиями;
- тёмная тема табло предусмотреть (отдельный layout без авторизации).

### F5. Линт и CI фронта — ✅ готово (job «Фронтенд» обязателен в branch protection)
- ESLint (typescript-eslint) + Prettier;
- job `frontend` в ci.yml: lint → `tsc --noEmit` → `vite build` (оба приложения);
- сборка должна проходить на заглушках.

**Критерий готовности основы:** Ф клонирует репо, поднимает бэк (docker compose +
seed --demo) и фронты одной командой, логинится под тремя ролями, видит меню и
заглушки своих экранов, имеет типизированный клиент и может вызывать любой эндпоинт
с автодополнением.

## 3. Фронтенд — экраны — владелец: Ф

Порядок = ценность для демонстрации. Для каждого: эндпоинты из Swagger-групп.

### E1. Регистратор · Утро и кабинеты
Утренний экран смены: кто из врачей ожидается, свободные кабинеты, закрепление
врача за кабинетом на день (учёт типа кабинета: УЗИ-кабинет — только УЗИ),
статусы «принимает/перерыв/закончил».
*Эндпоинты: «Регистратура · Утро и кабинеты».*

### E2. Регистратор · Пациенты
Поиск по СНИЛС / ФИО / телефону; регистрация нового: гражданство РФ/не-РФ,
СНИЛС опционален (приём без СНИЛС), для иностранцев — сторонняя страховка;
валидации полей как на бэке.
*Эндпоинты: «Регистратура · Пациенты».*

### E3. Регистратор · Запись и талоны (ядро, самый сложный экран)
- слот-пикер: специальность → врач → календарь свободных слотов → запись;
- отмена и перенос записи;
- живая очередь: выдача талона пациенту (номер);
- запись по направлению врача.
*Эндпоинты: «Регистратура · Запись и талоны», «Направления и перезвоны».*

### E4. Регистратор · Направления и перезвоны
Список направлений (к специальности) → запись по направлению; очередь заявок на
перезвон с внешнего сайта, статусы обработки (свежие сверху, лимит выдачи).
*Эндпоинты: «Регистратура · Направления и перезвоны».*

### E5. Врач · Мой день
Очередь талонов (ожидает / вызван / на приёме / пропущен), кнопки «Вызвать»,
«Не дождался», следующий пациент; начало/конец смены.
*Эндпоинты: «Врач · Смена и очередь».*

### E6. Врач · Приём
Карточка пациента, медкарта: жалобы, диагнозы по МКБ-10 (поиск по справочнику,
основной + сопутствующие), рекомендации; при необходимости — направление
к специальности; завершение приёма.
*Эндпоинты: «Врач · Приём и направления».*

### E7. Табло (ТВ)
Отдельный маршрут без авторизации: номера очереди, кабинет, принимающий врач,
вызванный номер с подсветкой; автообновление раз в 5–10 сек; крупные шрифты,
киоск-режим (полный экран). Доступ ограничен локальной сетью на уровне прокси —
на фронте ничего не проверяем.
*Эндпоинты: «Табло».*

### E8. Админ · Персонал
Учётные записи регистраторов и администраторов: создание, блокировка, сброс пароля.
*Эндпоинты: «Админ · Персонал».*

### E9. Админ · Справочники
Специальности и кабинеты (номер, этаж, тип/специальность кабинета).
*Эндпоинты: «Админ · Справочники».*

### E10. Админ · Врачи и график
Найм врача одной операцией (учётка + договор); недельные шаблоны графика
(редактор интервалов по дням недели); деактивация врача.
*Эндпоинты: «Админ · Врачи и график».*

### E11. Админ · Слоты
Генерация слотов из шаблонов на период; контроль слотов за дату (занятость по
врачам); блокировка слотов.
*Эндпоинты: «Админ · Слоты».*

### E12. Админ · Выгрузки
Выбор даты, скачивание вечерней выгрузки РФ / не-РФ (ручной эндпоинт).
*Эндпоинты: «Админ · Выгрузки».*

### E13. Внешний сайт (приложение `public`)
Информация о клинике и приёмные часы; график приёмов по специальностям
(не по врачам); форма «перезвоните мне» с валидацией телефона (7+ цифр).
Без авторизации.
*Эндпоинты: «Внешний сайт».*

**Общие требования к экранам Ф:** состояния загрузки/пусто/ошибка на всех экранах;
сообщения об ошибках из ответов API на русском; адаптив не обязателен, кроме
внешнего сайта (но таблицы не должны разваливаться); каждый экран — по реальным
эндпоинтам с типами из `shared` (никаких «временных» fetch без типов).

## 4. Девопс / деплой — владелец: Я

### D1. Прод-сборка
docker-compose: `db` (postgres:17 + volume), `backend` (uvicorn), `nginx`
(раздача сборок `staff` и `public`, прокси `/api` на backend).

### D2. Реверс-прокси и доступы
Маршруты: `/` — внешний сайт, `/app` — внутреннее, `/board` — табло (ограничить
локальной сетью по требованию AGENTS), `/api` — бэкенд.

### D3. Бэкапы
Ежедневный `pg_dump` в 19:30 (требование: потеря ≤ 1 день) + копирование каталога
выгрузок; скрипт восстановления + одна контрольная восстановленная проверка.

### D4. Секреты и конфигурация
`.env` на сервере (вне репо), `SECRET_KEY`, `CORS_ORIGINS`, `DATABASE_URL`;
проверка обязательных переменных при старте.

### D5. Процедура деплоя
Ручной скрипт: pull → миграции (`alembic upgrade head`) → сборка фронтов →
перезапуск. Проводить в окно 20:00–6:00 (по AGENTS). Зафиксировать в AGENTS.md.

## 5. Сквозной демо-сценарий (репетиция перед показом)

1. Админ: найм врача (учётка + договор) → шаблон графика → генерация слотов.
2. Регистратор: утренний экран → закрепить врачей за кабинетами (УЗИ-врач в УЗИ-кабинет).
3. Пациент на внешнем сайте: смотрит график, оставляет заявку на перезвон.
4. Регистратор: обрабатывает перезвон → регистрирует пациента (иностранец со страховкой) → запись на слот.
5. Внешний сайт: график обновился.
6. Пациент приходит → талон → **табло** показывает вызов.
7. Врач: мой день → вызов → приём: диагноз по МКБ-10 → направление к специальности.
8. Регистратор: запись по направлению.
9. Админ: вечерняя выгрузка РФ / не-РФ → файл в «облаке» (имитация).

Чек-лист: все шаги без перезапуска сервисов, на демо-сиде, с трёх ролями + ТВ.
